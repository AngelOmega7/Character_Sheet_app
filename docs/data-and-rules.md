# Reference data and stat calculations

**Current workflow update:** `workflow.md` supersedes earlier one-instance, purchasing, Transport, starter, and utility-roll behavior in this document. Current versions are `owner-corrected-v14`, `workflow-v15`, and save schema v10. There are 154 playable designs (54 CAUs, 6 FUZORs), 165 abilities, and four Transports. All BLOX designs and BLOX Type abilities are restored. FUZORs retain BLOX type and require multiple component Zoids at zero gold cost; selling restores saved pre-fusion component states, with fresh recipe copies as the fallback for old builds. Sale optionally retains the FUZOR's own identity and frame/weapon upgrades for a future rebuild. Buster Eagle, Fire Phoenix, and Jet Falcon remain Flying type; Zero Falcon and Zero Phoenix remain Liger type. NPC has zero style progression bonuses; new pilots start with Organoid None. Catalog Lion terminology is now Liger, except Saberlion's name.

## Delivered

- `tools/convert_reference_data.py` builds ten local JSON catalogs and a manifest from the local inventory. It never accesses Google Sheets.
- `zoids_app/catalog.py` loads local reference records by stable ID or trimmed display name.
- `zoids_app/stats.py` implements a deterministic calculation path for base, pilot-adjusted, and equipment-adjusted stats, carry penalties, fixed/removable weapon displays, selected abilities, frame/weapon upgrades, and Organoid bonuses.
- `zoids_app/preview.py` provides a runnable command-line preview before the Flet screens exist.
- `tests/fixtures/saberlion_snapshot.json` contains independently extracted cached spreadsheet expectations, not expectations generated by the new calculator.

Rules, data, and persistence modules use Python's standard library; the interface uses Flet. Pandas/openpyxl are not required for this conversion: the earlier inventory already contains the XML cell/table data needed. They can be added to development tooling later if needed.

Original sheet/row provenance, source headers, and original field values are retained. Text names are trimmed for display and ID generation; original names remain in the fields. Constant percentage formulas are converted to numeric fractions. Shared percentage formulas in Stats are resolved from their shared master. Character-dependent fields are marked with their formula and have **no cached value** in runtime data; they resolve against the selected character. In particular, Liger Zero's booster uses that character's computed speed, and the four armament templates look up that character's Zoid.

Per owner correction, legacy `NdM` weapon damage becomes the flat value **N × M**. Case and surrounding spaces are accepted: `18D10 explosive` becomes numeric damage 180, and `30d10 piercing` becomes 300. Weapon descriptions are converted inline too. Multi-shot wording is retained: “three bursts of 3D10” becomes “three bursts of 30,” with numeric damage 30 per burst, not 90. Supplemental wording from damage fields is retained in `damage_notes` and exposed as each calculated weapon's `damage_note`. Dynamic removable equipment inherits the converted value from its selected Zoid. Flat numeric values are unchanged; multiple dice terms in a single numeric damage field fail conversion for review rather than being guessed. Original values and source cells are preserved in `docs/generated/damage-conversions.json` and the untouched source inventory.

Description formulas are preserved for provenance; their cached text is used as reference prose. Feats remain descriptions, not automatically enforced turn/combat logic in this stat-calculation milestone.

## Pilot fields and feats

`Character.pilot_details` stores Physical and Social (integer tracking values), Personality, general inventory/cargo notes, Zi Database/campaign notes, and up to seven ordered feat selections. Names are canonicalized to stable feat IDs; blanks are empty slots. The editor displays each selected feat's description. These fields are saved pilot-wide and do not feed stat, heat, repair, or dice calculations. Eligibility/effects are handled at the table, including advantage and Demolitionist's multi-weapon Vent. Mental retains its existing reaction calculation.

Source mapping: Physical/Social were Pilot!C4/C6; the general inventory area was G4:N11; the database area began at J13; feat slots were B41:B47. Source Personality (C7) displayed Organoid color through a formula; the app now provides independent editable tracking text. Old saves default these newly tracked fields to zero/blank/empty rather than copying the workbook's example pilot.

## Model and API

```python
from zoids_app.stats import CharacterBuild, Upgrades, calculate_stats

build = CharacterBuild(
    zoid="zoids:saberlion",
    pilot_style="FIGHTER",
    pilot_level=1,
    mental=3,
    abilities=("abilities:lion_type_1",),
    upgrades=Upgrades(damage=(1, 0, 0, 0)),
)
stats = calculate_stats(build)
assert stats["pilot"]["health"] == 144
```

Upgrade inputs are **points**, each 0–5. Frame multipliers are speed 30, reaction 1, defense 5, capacity 10. Fixed weapon damage is 20/point and to-hit is 1/point. Only fixed slots 1–4 accept either weapon upgrade. Per owner clarification, to-hit upgrades also add a flat +1/point to the final attack bonus after pilot/modifier rounding; pilot percentages and overload penalties do not scale this added bonus. Slots 5–8 receive no weapon upgrades. The workbook's saved E12 value of 20 is imported as one damage point, not 20 points. The character-management layer now records upgrades, rejects upgrades on empty/utility slots, and shares them by owned chassis and weapon identity as described below. Purchase costs/eligibility beyond those slot restrictions remain future work; the calculator itself applies a supplied build.

## Owned Zoids and CAU forms

`characters.py` stores a pilot's `owned_zoids`, with a unique instance ID for each owned base; duplicate chassis are supported. The active selector uses that roster rather than the entire catalog. `acquire_zoid()` records acquisitions; `switch_zoid()` flushes the current loadout/upgrades before projecting the chosen owned form into `CharacterBuild`. BLOX-type Zoids and all five BLOX Type ability ranks are restored. Source types are trimmed for exact matching, including `BLOX `.

Hover Cargo, Gustav, and Whale King are moved into `transports.json` and the UI's **Transport** reference section. Their source fields and provenance are preserved. They cannot be acquired or selected as normal playable Zoids. Carrying other Zoids and storing unused collected Zoids are deferred Transport features.

CAU forms must be acquired separately after their base:

| Base | Obtainable CAU forms |
|---|---|
| Liger Zero | Zero Jager, Zero Schneider, Zero Panzer, Zero X, Zero Empire, Zero Falcon, Zero Phoenix |
| Konig Wolf | Konig Wolf DSR |
| Berserk Fury | Sturm Fury, Jagd Fury, Berserk Fury Z, Buster Fury |

All listed form catalog names include `(CAU)`. No other source `base_zoid` relationship automatically creates a shared ownership family.

- Frame speed/reaction/defense/capacity upgrade points belong to the owned base and apply to all its obtained forms.
- Fixed-weapon damage/to-hit points use stable weapon identities. A form weapon matching the base weapon shares upgrades in both directions, regardless of slot. For example, Liger Zero's slot-3 Strike Laser Claw and Jager's slot-4 Strike Laser Claw share points. Form-specific weapons are independent. Identically named weapons on another owned chassis do not share.
- Strike Laster Claw, Strike Laser Claw, and Strike Laser Claws are standardized to **Strike Laser Claw**, with original names retained in correction metadata. The authoritative converter emits explicit CAU ownership and weapon-identity metadata.
- Each form keeps its own equipment and activation flags. Current health, shield damage, and defense adjustments belong to the owned chassis and persist through form changes; switching to another owned chassis restores that chassis's resources. Pilot selections/abilities/Organoid settings and gold remain pilot-wide. Calculated maximums are recomputed without healing.
- The UI records upgrade points and acquisitions without charging gold. Purchasing rules remain pending.
- SQLite schema v7 adds pilot tracking fields/feats and migrates v1–v6 transactionally while retaining roster, inventory, combat state, last rolls, and archives. Prior Zaber Fang positional builds/activation flags are adjusted to the corrected weapon layout, preserving Killer Saber's identity-based upgrades/conditions in slot 4. Older conditions get an empty last result without rolling; pre-combat weapons start at zero heat/intact. Invalid data aborts without partially converting the database.
- Saves use SQLite schema v10, including preserved FUZOR component states and optional retained FUZOR identities/upgrades. A single saved character can be exported as a versioned UTF-8 JSON document and imported through the normal decoder/migrations. Import validates the character, never overwrites an existing ID (a collision receives a new ID), and rejects unsupported format/save versions or invalid data without partial writes.

Equipment and fixed activation flags are independent of attacks, heat, and broken status. The combat controller blocks use of broken weapons and updates weapon conditions separately from activation. Calculations never modify current health, shield damage, gold, heat, or weapon condition. Numeric arithmetic uses Decimal and explicit spreadsheet half-away-from-zero / away-from-zero rounding.

## Persistent combat state and commands

`WeaponCondition` stores nonnegative heat, a Boolean broken flag, and `last_roll` (None or an integer 1–20) independently of derived heat rating/capacity. Each inventory copy has its own condition. Each owned chassis has fixed-weapon conditions keyed by shared weapon identity, so CAU changes (including moved slots) preserve them; non-weapon utility equipment uses a form-specific slot identity. A different chassis or duplicate inventory copy has independent condition. Unequipping does not clear heat, repair the item, or discard its roll.

`combat_controller.py` provides validated, atomic `weapon_action()` (Use/Vent/Repair), `rest_active_loadout()`, `repair_character_health()`, read-only `combat_snapshot()`, and `attack_preview()`. It uses the existing combat rules and latest calculated maximum health/capacity. Failed actions leave the supplied character unchanged. Health and shield damage remain per chassis; gold remains pilot-wide.

- **Use:** after validation and broken-state checks, roll exactly one d20 (inclusive 1–20) and store its raw result in the weapon's Last d20 box. Rated equipment adds one heat; a use at/above capacity rolls/resolves and then breaks the weapon. Further uses fail without rolling until repaired. Unrated equipment also rolls, but does not accumulate heat. Apply attack modifiers separately; a die result does not automatically establish a hit.
- **Vent:** remove one heat, floored at zero, without repairing.
- **Rest active loadout:** zero heat on the current eight-slot loadout; preserve health, shield damage, gold, and broken status. Unattached or unrelated form-specific weapons are not cooled. Shared identities still refer to the same physical weapon.
- **Repair health:** restore requested points (blank/full in the UI) at 10g per point actually restored, based on current derived maximum. Heat, shields, and weapon condition are unchanged.
- **Repair weapon:** 10,000g for one broken weapon; clear its heat and broken status. Intact weapons cost nothing and are not cooled. More than 25% missing health requires the Flet Cancel/Repair anyway confirmation; an altered character/weapon invalidates the quote and requires a fresh click/quote.
- **Resource fields:** current health, shield damage, and gold accept nonnegative whole numbers. The shield display is floored at zero remaining HP while saved shield damage stays unchanged. Resource changes do not happen merely because maximums recalculate.
- **Persistence:** Save character retains current resources, fixed/removable conditions, and the most recent raw result per weapon identity/copy. Vent, Rest, and repair preserve that result. Previews, refreshes, range choices, and save/load never reroll, increment heat, or spend resources.

## Owned removable equipment

`zoids_app/equipment.py` supplies catalog compatibility rules: Assist slots accept only equipment below the ASSIST heading; Weapon and Assist slots accept equipment from the whole Armaments sheet, including dynamic Zoid equipment templates. Headings/placeholders are not equipment choices. Empty source slot types have no choices. `resolved_equipment_name()` displays a dynamic template under the actual name for a given Zoid (for example, Command Wolf's Double Beam Cannon), while retaining the generic fallback when the Zoid has no such equipment. The build-level `equip_item()` helper remains useful for rule calculations, but does not manage ownership.

The editor and saves use `characters.py`: `acquire_equipment()`, `available_equipment()`, `equip_owned_equipment()`, `return_equipment_to_inventory()`, and `delete_equipment()`. Each `OwnedEquipment` copy has a unique ID and an Armaments reference. Each form's `equipment_ids` links its four removable slots to those copies; the calculator still receives resolved catalog IDs. Validation checks both references match, rejects unowned copies, and enforces allocation across the complete roster.

- A pilot may own multiple copies of a type; acquisition accepts a positive whole quantity. Unattached items remain in inventory and do not contribute weight or bonuses.
- Dynamic Zoid-specific templates are offered by their resolved names in the acquisition menu for each owned Zoid/form. Generic template labels display as overall equipment slots 5–8 after fixed weapons 1–4; stable catalog IDs remain `armaments:zoid_equipment_slot_1` through `_4` for save compatibility. A copy still resolves against whichever Zoid it is equipped to, so inventory labels follow its current assignment (or the active form while unattached).
- A copy may appear once in each alternate form of the **same owned Zoid**. It cannot appear in two slots of one form or be assigned to different owned Zoids. Assignments on inactive forms still reserve the copy for their chassis.
- Clearing a slot returns that form's assignment; if another form references the copy, it stays assigned to the same chassis. **Return to inventory (all forms)** clears every assignment so another Zoid can use it. Neither operation deletes the owned copy.
- **Delete copy** permanently removes one unattached copy after confirmation. Equipped copies must be returned to inventory from all forms first. Stored heat/broken status is discarded with the copy; gold, Zoids, upgrades, and other copies are unchanged.
- Attaching a different copy or clearing a slot resets its activation. Reselecting the same copy preserves activation. Other loadouts, upgrades, resources, and gold are preserved. Acquiring copies records ownership without charging gold.
- Migration creates the minimum copies needed by each legacy owned chassis: the maximum simultaneous count of each type across its forms. Corresponding copies are reused across forms, while different chassis receive separate copies. Stable IDs persist on subsequent loads; retirement archives are untouched.
- Acquisition/learning and equipment-slot dropdowns use Flet's native case-insensitive text filtering and retain scrolling. Typing alone changes no ownership or assignment; acquisition buttons reject a stale selection when its visible search text no longer matches.

## Ability ownership and size bonuses

`zoids_app/abilities.py` manages an `AbilityLoadout` with active and inactive lists. `CharacterBuild.abilities` contains up to six active slots; `inactive_abilities` stores owned abilities that contribute no bonuses.

- At most **one size bonus ability** can be active, even if a second ability targets a different size. Multiple size families may be owned inactive.
- Numbered names are ranks of one ability family; an unnumbered name is rank 1. Family matching ignores capitalization. BLOX Type 1 retains the source typo `BLOXType 1` as a legacy alias; all five ranks are available.
- `learn_ability()` places a new family in inactive storage. A higher rank replaces the owned lower rank in its existing active slot or inactive position. The lower rank is removed, not moved to inactive storage. Downgrades are rejected.
- `activate_ability()` moves an owned inactive ability into a chosen slot, storing the displaced ability inactive. It rejects a second active size ability in another slot. `deactivate_ability()` moves the selected ability inactive.
- Calculation validates both lists so duplicate ranks/families cannot sneak into a build. The editor uses validated learning/assignment transitions through `learn_pilot_ability()` and `assign_pilot_ability()` in `characters.py`; save/load validates and persists both lists. There is no separate historical rank ledger.
- Size matching uses exact, case-insensitive categories. `Large` does not match `Extra Large` or `Large Large`. Comma-separated categories such as `Medium, Small` explicitly support both sizes.
- The matching size percentage contributes to health, armor, reaction, range, and now **all eight weapon to-hit modifiers**. It adds to the pilot percentage before multiplication/rounding. Fixed-weapon flat to-hit upgrades are added afterward.
- Medium Under Expert 4 is corrected to **0.25 (25%)**. The original value 25 and reason are retained in the record's correction metadata.

Example: base to-hit 17, pilot bonus 25%, size bonus 10%, and two fixed upgrade points give `ROUND(17 × 1.35) + 2 = 25`.

The **Abilities** panel lists learnable new families/higher ranks with descriptions, six active slot selectors, and inactive ownership. A new family is learned inactive; a higher rank replaces its predecessor in its existing active slot or inactive position. Assignment only offers owned inactive abilities plus the slot's current selection; **Empty / deactivate** returns an active ability to inactive ownership. A second active size ability is rejected atomically. Player-managed effects retain descriptions. These pilot-wide lists survive Zoid/form switches and also work without an owned playable Zoid. Stat-affecting changes refresh immediately; weapon-card previews include contextual Sniper/Comeback effects.

## Organoid activation

All Organoid contributions are gated by `CharacterBuild.organoid_enabled`. Selecting a color and level alone grants no bonuses. When activated, the Organoid's to-hit percentage now contributes to all eight weapon slots, alongside the pilot and matching size percentages, before rounding. Flat fixed-weapon upgrades are added afterward.

The **Organoid** panel provides White/Red/Blue/Black, levels 0–40, and an activation toggle. Changes immediately recalculate stats without resetting current health, shield damage, or other resources. The character/save layer validates selected color/level even while deactivated. Settings persist pilot-wide across Zoid/form changes and reloads.

Example: base to-hit 17, pilot bonus 25%, size bonus 10%, Black level 5 Organoid bonus 25%, and two fixed upgrade points give `ROUND(17 × 1.60) + 2 = 29`.

Deactivation removes the Organoid contributions to maximum health, armor, speed, range, shields, weapon damage, and weapon to-hit. It does not alter saved current health, shield damage, heat, gold, or weapon condition. Tests cover activation/deactivation for all four colors and confirm the complete calculated result returns to its non-Organoid baseline. Only activated White Organoids generate shields, once, using Organoid level; Red/Blue/Black never generate shields. Pilot level and equipment activation flags do not control Organoid shields. The damage-column discrepancy listed below remains deferred.

## Active speed and contextual attack abilities

Fleet Footed ranks add their existing +50/+100/+150/+200 speed values whenever active. These are flat additions to current speed after base/pilot/Organoid calculations, alongside equipment bonuses. Inactive owned skills contribute nothing. Slowpoke and the other retired drawback families are removed.

`zoids_app.attacks.calculate_attack()` previews a selected weapon's attack modifier and flat damage using current health and a per-attack range selection. It is separate from `calculate_stats()` because range and current health are attack context, not reference data. It does not roll, fire, change heat, check broken state, or spend resources. The editor displays these previews separately from the combat controller's Use action, which enforces broken-state and heat rules.

- **Sniper 1–4:** +1/+2/+3/+4 to-hit, only when active and the selected ranged attack is Long Range. This is not a maximum-range bonus. Both fixed and removable ranged weapons are eligible.
- **Comeback 1–4:** +20%/+30%/+40%/+50% damage, only when active and current health is **at or below 20%** of the latest calculated maximum health. This applies to melee and ranged attacks. Percentages add to Organoid damage percentage on the base damage plus fixed damage upgrades, with one final spreadsheet-style rounding; they do not multiply one another. Original descriptions/values are retained in correction metadata.
- **Range controls:** Close Range is <=60m; Normal Range is >60m and <=half current maximum range; Long Range is >60m and >half current maximum range. Weapon cards have one mutually exclusive selection for ranged attacks, hidden for melee. Normal is omitted when the maximum range leaves no Normal band. The API additionally accepts an optional distance. Range is transient per-weapon preview context, not a saved resource or a use/roll trigger.
- **Boundary:** Close takes priority through 60m, including for short maximum ranges. Exactly half maximum range is Normal only when above 60m. This replaces the earlier unconditional half-range boundary and overlap error.
- Ranged classification uses the `Ranged` damage-type tag, excluding `Melee`. Ranged Piercing weapons have Piercing removed and Ranged + Bullet tags. Command Wolf IS's Zoid-specific Long Range Rifle retains its earlier explicit Ranged correction.
- Ranged Energy tags are now Laser. Laser Expert requires Laser only; melee Energy is retained but no longer qualifies. Source-declared Ranged classes/descriptions have been reflected in tags, including the owner-classified Zaber Fang RS cannon. Current named positive-damage Zoid attacks are classified in the live tag columns.

See [Ability review](ability-review.md) for the remaining ability discrepancies and descriptive effects awaiting implementation.

## Source issues requiring owner decisions

### Equipment activation correction

Each removable equipment slot contributes its own armor, defense, reaction, speed, range, to-hit, and shield bonuses only when that item is passive or its activation flag is on. A passive item contributes automatically while equipped, including in the chest slot. Empty slots contribute nothing. Activation never enables bonuses from another inactive item. Equipped weight still counts whether an item is activated or not.

The fixed slot 2/3 speed, range, to-hit, and reaction modifier fields also use their own activation/passive state. Ability reaction bonuses remain additive. True Tank applies per enabled defensive item; Evasion Master adds Armor per enabled reaction-boosting item. Shield Master adds to the combined positive Shield HP pool independent of source. See `ability-review.md` for the confirmed rules.

Shield-producing equipment units 1–8 use their own activation/passive state. The source has fixed shield fields only on units 2 and 3; these now map to fixed activation flags 2 and 3, respectively. Removable units 5–8 each contribute independently. Organoid shields are separate from equipment activation.
